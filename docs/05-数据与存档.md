# 数据与存档

更新日期：2026-11-13。本文定义Godot目标数据合同。项目没有数据库，不建立、连接或修改数据库；所有游戏数据均为随包配置与本地文件。

## 1. 数据分层

| 分类 | 内容 | 持久化方式 |
| --- | --- | --- |
| 正式配置 | 地图、职业、成长、武学、装备/披风、物品、配方、任务、怪物、掉落、NPC服务和资源清单 | `res://assets/config/*.json`，只读 |
| 本地档案 | 档案ID/名称、角色列表、档案设置 | 每档案一个JSON文件，一次提交 |
| 角色进度 | 身份/职业/外观、成长、货币、装备、背包/仓库、技能、任务、门派、随机序列、位置 | 档案内独立角色快照 |
| 普通战斗现场 | 普通敌人短期生命/AI、掉落、竹命中/刷新、投射物、路径 | 不写角色存档，重建现场；角色计时与活动快照另存 |
| 角色计时与活动 | 角色冷却/效果剩余时间、装备切换剩余时长、进行中活动逻辑快照与结算ID | 写入角色；离线不推进，恢复不重抽或刷新 |
| 会话界面 | 消息、草稿、筛选、地图路标、预览、未确认数量与操作 | 不持久化，退出清理 |

角色、装备、物品、职业、地图、NPC、配方与任务均使用稳定ID，展示名可调整。节点路径、ObjectID、Resource句柄、动画播放器和内存地址不能写入存档。

## 2. 配置与严格校验

| 配置 | 职责 |
| --- | --- |
| world / exploration | 地图对象、区域、出生点、安全区、连续碰撞、镜头和移动 |
| classes / skills | 完整职业体系、武器条件、主动武功、被动气功、晋级与路线 |
| items / equipment | 堆叠物、唯一装备定义、槽位、披风、属性、操作限制和商店价格 |
| crafting / upgrades | 强化概率/费用、合成孔、石头适配、洗炼、转移和制造配方 |
| gameplay / quests | 成长、战斗、怪物AI、掉落组、任务与门派规则 |
| assets | 正式场景、模型、材质、骨骼/命名动画、字体、音频与许可引用 |

按实际职责组织JSON，避免同一数值出现在多个正式文件。旧RON一次性转换并逐字段对照；新增系统完成后不维护两份正式配置。

拒绝未知/缺失字段、类型错误、重复ID、非法枚举、非有限值、越界、负数、经验阈值乱序、概率和权重非法、时序矛盾、资源越界路径、无效引用、出生点碰撞、无效掉落和配方环。错误给出文件、字段路径与原因。

JSON数字解码后必须验证整数性与范围，不能用 `int()` 截断非法小数。旧格式无符号字段仍按0～4294967295校验；新schema5经济字段使用64位整数，并限制在JSON可精确表达的0～9007199254740991，必须覆盖官网50亿银两等需求，不能沿用32位上限导致高阶转职无法完成。随机状态用固定格式字符串表达，避免JSON浮点精度丢失64位状态。

## 3. 档案目录与提交单位

Windows默认根目录为 `%LOCALAPPDATA%/SoloRxjh/`。新档案文件为 `profiles/<profile_id>.json`，文件名与内部ID必须一致。通过枚举档案文件展示本地列表，不另存一份容易失配的角色索引。

每档案最多6角色，角色快照、外观和设置置于同一个档案文件；一个角色保存时复制档案、更新该角色、完整校验再提交。这样创建、删除和选择记录不跨多个文件产生半份状态。角色间背包、仓库、货币和随机序列不共享。

`--save-dir PATH`覆盖整个存档根目录，测试必须显式指定隔离目录。缺失LOCALAPPDATA时明确报错，不能猜测其他位置。未知档案、损坏JSON或不兼容版本显示原因，不自动重置、删除或读入临时文件。

## 4. 新格式

目标档案格式为 `schema_version=5`、`content_version=jianghu-godot-1`。这是新增多角色/职业/装备结构导致的版本变化，不因引擎名称变化随意改旧档版本。

| 字段 | 约束 |
| --- | --- |
| profile_id / profile_name | 唯一且与文件名一致；名称满足界面规则 |
| selected_character_id | 为空或指向档案中确实存在的角色 |
| creation_unlocks | 当前版本若有档案级职业创建资格，保存已完成解锁任务与资格；明确配置校验，不以缺字段默认全部开放，角色资源仍独立 |
| settings | 主/音乐/音效/UI音量、镜头、窗口/分辨率、图形预设与垂直同步，范围严格校验 |
| characters | 最多6个，角色ID与姓名在档案内唯一 |
| character.identity | 姓名、职业、体型、肤色/发型/配色、创建时间 |
| character.progress | 累计经验、生命/内力/体力、银两、历练、十二转等级/路线、各阶段晋级任务、升天历练/天机石/点数、主线/区域进度、门派 |
| character.inventory / equipment_bag / warehouse | 容量等级、堆叠物和装备实例；不允许同一实例出现在两处 |
| character.loadouts / active_loadout_id | 明确主/辅助组及当前生效组，按完整槽位定义保存；组ID有效，定义/资格/实例归属严格校验，备用不叠加属性，不冻结旧11槽 |
| character.gems | 独立6位：武器、衣服、内甲、护手2、靴子；类型、品质与实例归属校验，当前有效性由角色资格/对应装备重新计算，不存一份可能失配的加成 |
| character.skills / qigong | 普通/升天武功、普通/升天气功、反气功、已学秘籍、分配点数与前置；派生有效等级不另存 |
| character.quests | 主线、区域、晋级、披风、制造、扩容与委托的唯一进度/领奖记录 |
| character.random_state | 固定格式种子和消费位置，战斗/掉落/强化使用同一明确序列 |
| character.timers / effects | 技能/药品冷却及角色效果剩余世界步、来源/叠加标记；装备组剩余交互时长另记，不从保存日期推算 |
| character.activities | 活动轮次/尝试ID、入场提交、阶段、时限剩余、必要逻辑快照、已结算事件；空活动明确为空集合 |
| character.customization | [18配置中心](18-角色参数配置中心.md)的覆盖版本、显式字段与最近配置记录；空覆盖为空映射，不复制全部全局定义 |
| character.location.map_id / position / yaw | 明确场景ID、有限坐标、合法入口/位置、非阻挡位置与安全高度；不能只存一组无场景归属的坐标 |
| character.saved_at | 保存时间只作展示，不决定奖励、刷新或限时付费 |

装备实例包含唯一ID、定义ID、类型化成长数据与来源。普通装备的强化/合成、进化/提真/武勋等分开；宝珠保存自身品质，不把一个随机稀有度倍率用于所有武器防具。各类型所需字段必须明确校验，不增加无用途字段或缺值补普通。披风引用已解锁外观/显隐，预览不写正式装备。实例ID不可复用，同名装备不因排序合并。

所有权、主动装备条件、当前生效条件分开。官网明确宝珠在隔体传功后保留原角色而暂时失效，资格恢复后重新有效；该合法状态不能静默删物或一概拒绝读取。主动穿戴仍检查140级/四式等条件，未知定义、错误槽位、重复实例和未声明状态不能借此放行。主/辅助切换不得复制装备、刷新技能冷却或把两组属性同时生效。

等级、最大生命、最终攻击防御、护体后伤害、气功有效等级、任务门开关及已击败首领由持久进度推导，不能存两份相互矛盾的值。

U33允许角色自定义覆盖：等级仍由经验推导，最大生命/最终攻防等先计算规则值再应用明确覆盖；覆盖不是另一份派生缓存，清除时重新计算。配置中心直接修改实际物品/任务/资源进度，并记录配置来源，不产生第二份角色数据。正常玩法合法状态与用户配置例外显式区分；未知定义、重复实例、非法JSON仍拒绝。

职业起点按[14采用合同](14-职业创建与成长采用合同.md)显式配置：本项目新建角色1级0转是改编，历史80级0转乐师只在参考库保留，不直接导入为新建模板。等级与已完成晋级仍独立校验，不按等级自动补任务。创建初始化、晋级与初始装备授予均有独立去重标记；不因当前直接创建方案而放松未知资格字段检查。

### 4.1 计时与活动快照

世界时间使用60Hz整数步，持续2小时为432000步、20分钟为72000步、眩晕10秒为600步。剩余步数须为非负整数且不超过对应规则上限；角色效果包含定义ID、来源事件、层数及必要触发状态，不保存可失配的最终属性加成。装备组冷却保存剩余整数毫秒0～1000；离线冻结，不保存系统单调时钟绝对值。

普通敌人现场重建不清除角色冷却、负面状态或成功BUFF；死亡、解除或技能明确改变效果时按对应规则执行。角色未完成动作跨保存需要保存动作ID、剩余阶段、已扣资源及已命中集合，或只在动作结束后捕获保存；不得保存已扣费却遗漏待结算动作。正式实现选择“动作结束后捕获”，活动战斗快照除外。

进行中讨伐必须在固定步边界保存逻辑快照：玩家和9名伙伴及敌人的稳定实体ID、位置/朝向、生命/资源、动作阶段/剩余步、冷却/效果、仇恨/目标；召唤物、未结算投射物及命中集合；安全罩/红区/人数圈/四珠状态、阶段进度、弱点计数、时限和随机消费位置。只记录存在的逻辑状态，不保存NodePath或引擎句柄。

活动保存不退回阶段开场，不重置敌我生命、已消费道具、机制进度或随机序列。恢复先验证全部定义/实体引用和阶段一致性，再重建表现；失败明确报错，不清空活动继续玩。胜利或失败提交时移除活动现场快照，保留尝试与奖励结算记录；退出后不额外重新生成同次掉落。

角色手动保存、暂停退出和自动保存均捕获同一一致状态；活动战斗中允许快照，普通未完成动作则等到动作结束再捕获。若无法取得一致状态，显示尚未保存，不提前写“保存成功”。这些是待实现合同，必须实测持续伤害、飞行投射物、濒死及机制倒计时的保存往返。

## 5. 旧档兼容与导入

已知历史格式为schema1/liuli-0.3、schema2/liuli-0.4、schema3/liuli-0.5、schema4/liuli-0.6。旧单槽路径为根目录 `save.json`；只通过明确的导入操作读取，不自动覆盖或移动源文件。

迁移先按原版本严格校验，再逐级转换：补武学/历练/门派、把固定强化转为装备实例、生成稳定且不重复的实例ID，最后写入新档案中的方尘剑客角色。旧ID、经验、银两、背包、装备强化、任务/区域、贡献和位置保留。

新字段明确初始化：旧角色未转职、未选正邪、内力按目标版当前等级满值、额外装备槽为空、仓库为空、旧装备容量不缩减；原装备保持原定义/强化，不新增虚构随机品质。既有剑客武功等级保留，不扣新学费；气功分配为零。若旧角色等级已满足转职，只开放任务，不自动标为完成。

旧7件装备定义继续可解析：`fuxian_sword / ironwood_blade / refined_blade / frost_edge / menial_robe / leather_armor / dark_iron_armor`，保持原属性，不能借迁移替换成不同条件的新装备。未知版本、缺失定义、非法槽位、重复实例、超上限强化、矛盾任务/贡献拒绝导入，不丢弃错误记录继续运行。

旧单场景档案明确映射到对应旧世界场景ID，保留原坐标与朝向并校验；不能因地图扩充悄悄传送、重置或把旧坐标放到另一个场景。新副本记录入口、难度、任务/奖励结算与退出恢复边界，临时怪物和地面物仍按场景现场规则处理。

主线阶段保留 `report → take_sword → bind_sword → gathering → challenge → return_to_outpost → completed`；区域阶段保留 `valley_hunt → valley_boss → valley_report → north_hunt → north_boss → north_report → completed`。两者与新增转职任务分别记录。

## 6. 保存流程与故障要求

1. 固定步事务完成后捕获一致快照，死亡状态延迟至返回工棚。
2. 复制档案，替换当前角色，完整验证所有角色、实例、设置与引用。
3. 目标文件同目录写唯一临时文件，拒绝占用已有临时文件；写入后flush并关闭。
4. 通过DirAccess在同文件系统提交替换，只有成功才更新“已保存”。不先删除旧档。
5. 失败保留旧文件和当前内存进度，显示路径/原因，清理本次创建的临时文件；旧临时文件不自动覆盖或当作有效存档。

FileAccess/DirAccess替换已有文件、权限拒绝、异常中断、磁盘写入失败和旧文件保留都必须在Godot4.7.2/Windows下实测。不能沿用Rust版ReplaceFileW的通过结论，也不能在失败时改成删除旧档再写。

成功事务触发自动保存；失败保存不撤销已经完成的内存玩法事务，但必须保持“未保存”状态。重新退出前需要确认；不得显示保存成功后静默丢失进度。

## 7. 事务与测试隔离

### 7.1 局域网与多开补充

同一档案文件仅一个实例持有写锁；不禁止不同档案/独立根的多开。锁获取失败不偷偷改路径或复制存档，异常锁按实际进程与系统文件锁判断。[19联机合同](19-局域网组队聊天与多开.md)要求客户端只保存自身角色、房主保存世界和持久结算日志：新增`worlds/<world_id>.json`，同目录原子替换，包含协议/规则版本、参与角色修订、活动/队伍状态及待确认/已确认结算ID。

网络命令去重使用`world_id + character_id + settlement_id`，不使用会重分配的Peer ID作为持久身份。房主日志持久成功后才发结果，客户端应用/存档成功后确认；重连只重放未确认结果，客户端持久去重。跨文件/跨机器未确认状态须明确展示，不宣称全体同时原子保存。房主失败不发已提交结果，客户端失败不重抽或重复扣票。

每笔记录包含世界序号、请求ID、规则版本、前置世界修订号、随机前/后状态和全部参与者结果。各参与者保存角色ID、结算序号、前/后修订号、变更及校验后的结果快照、确认状态。多人经验、门票或掉落一次业务提交写入同一房主文件，不能先通知一人成功、再因另一人写入失败回滚半笔。

房主流程为校验→在副本计算世界/角色/随机结果→持久写入新世界快照与待确认日志→发布内存结果和网络消息。日志写失败整笔不提交，保持原随机状态；成功后崩溃则按日志恢复，不再次计算随机。房主自己的角色也作为接收者写入档案并确认，不能假定房主两个文件天然原子。

客户端收到结算时要求前修订号等于当前已提交修订，按序应用结果和`network_receipts`到同一档案快照后确认；保存失败保留待保存内存，暂禁该角色新的经济/任务/配置事务，不阻止其他玩家。重发同笔只重试保存/确认；序号缺口请求缺失结果，不跳过。不能把重复结果当重新获得的经验/物品。

`character.network_receipts`按world_id保存最后连续应用序号及角色结果修订；房主按角色保存连续确认水位。仅当该业务全部接收者确认、世界新快照已成功持久后才能压缩对应完整事件；角色修订、确认水位和必要最终快照保留。旧序号重试只回复已提交状态或同步快照，不重新发奖。未确认事件不按天数或条数自动丢弃；空间不足明确停止新业务并提示，不删除记录继续游戏。

重连先比对世界ID、角色ID、协议/规则哈希、接收水位及前置修订。客户端离线另改角色或导入造成分支时拒绝直接合并，并显示两边修订；用户可退出房间继续本地分支，或先导出本地角色再明确恢复房主保存的分支。禁止按时间戳自动选择、覆盖或把差额再次结算。手动回滚/篡改本地文件不在防作弊承诺内，正常保存链的重试去重必须保证。

聊天记录不持久化，房间口令不写角色/配置方案；房主结束世界保留必要结算记录。日志清理按连续确认水位执行，断线角色的10秒实体/120秒席位规则见19合同；普通角色单机文件规则继续有效，数据库始终不使用。以上字段均为计划结构，Windows替换故障与多进程实际实现仍未验证。
