# 物品堆与数量来源校验合同

更新日期：2026-11-14。状态：**当前堆结构与数量来源设计采用，未实现；完整档案与经济收据仍待**。结构化权威为[物品堆与来源JSON](contracts/物品堆与来源.v1.json)，结构校验分别见[堆schema](contracts/物品堆.schema.json)和[来源流schema](contracts/物品堆来源流.schema.json)。

## 0. 正文注册表与完整位置布局

[容器与仓储JSON](contracts/容器与仓储.v1.json)的`persistent_layout`明确布局权威，[布局schema](contracts/物品容器布局.schema.json)覆盖三容器、两组14装备槽、6宝珠位、当前组及库存修订。它是完整位置结构片段，仍需与全部物品正文、角色及收据组合校验。

`character.item_stacks`按堆ID唯一保存当前堆正文，`character.equipment_instances`按实例ID唯一保存当前实例正文。键必须等于正文身份。三容器各精确保存`expansion_level/slots`，只记录占用格；每条精确为`slot_index/kind/target_id`。槽号0起、严格递增且不重复，未出现的索引为空格，容量由17扩容式推导。材料包只引用stack，装备包只引用instance，仓库按实际仓储权限引用两者。

两套装备各14槽及共享6宝珠位只存实例ID或显式null。主辅组只选`primary/secondary`，备用物品仍占一个正式位置并计重。每条正文恰好被一个正式位置引用；孤立正文、悬空引用、同ID多处、重复槽号、错误类别或owner均拒绝，不读档重排、删物或猜位置。

布局schema拒绝扩容等级和索引越界；完整引用、逐物品类型、任务/装备资格、负重和来源须另外检查。未完成类型的实例不能用空object或原样JSON放行。合法暂失穿戴资格按原owner保留，不能把所有不生效实例当坏档删除。

库存实际变化每事件只增加一次`inventory_revision`，同事件多个位置不重复计数；纯预览和无变化排序不增加。正式新建以三0扩容空容器、两空正文表、两组空装备及6空宝珠位、主组primary、库存修订0作为礼包前基线，实际礼包在唯一创建结算内写正文/位置/来源并增修订。四组已知旧档导入保实际物品与原分区顺序，按定义拆合法堆预检空间，不免费扩容或丢超量物品；现有新格式缺字段拒绝。复购保管独立于当前持有注册表，其故障适配仍待。

## 1. 当前堆的唯一状态

堆根精确保存七字段：`stack_id/item_id/binding/quest_scope/quantity/revision/origin_receipt_id`。数量为严格整数1～9999，且不得超过实际定义上限；装备、披风、宝珠等唯一实例不进入此结构。角色容器及槽位唯一决定当前归属和位置，不在堆内复制owner、位置、重量、单价或堆上限。

普通物品的`quest_scope=null`。不绑定物必须`binding=unbound`且无任务作用域；角色绑定物的绑定角色就是外层角色，不能搬到另一角色后重新解释。

任务作用域必有`quest_id`，其余只写对应定义声明的维度：

| 已采用的绑定 | 额外字段 | 校验依据 |
| --- | --- | --- |
| 角色与任务 | 无 | 该角色对应任务的真实物品来源 |
| 接取轮次 | attempt_id | 当前或owner明确保留的原轮次 |
| 路线分支、职业 | branch_id、class_id，按定义选择 | 精确任务分支和职业，不能读当前角色值后补历史 |
| 世界日 | world_id、accepted_day_index | 修炼任务接取世界与接取日 |
| 前置完成 | completion_receipt_id | 推荐书真实前置最终收据；不绑定后续主任务轮次 |

schema允许的可选字段不是随意增添字段的权限；运行校验须逐定义检查作用域键集合和值。完成凭证不混用attempt或世界日。任务日界和放弃按原owner清理实物并记收据，不另存一份可矛盾的剩余时长。当前正式堆没有独立通用限时实物格式；将来采用时须明确版本与迁移，不能按缺字段默认永久。

合堆键精确为定义、绑定和完整任务作用域。来源不同可以合堆，数量来源仍全部保留。对象键顺序不影响比较；显示名、排序位置和同名任务物均不能替代身份。

## 2. 拆分、合并与修订

新堆修订0。数量或实际作用域/来源改变的存续堆，每事件只加1；达到安全整数上界不能回绕。纯排序、同角色整堆移仓保堆ID和内容修订，只更新外层库存修订，仍重查预留、权限和保护量。部分移仓、合并及消耗必须产生数量流。

源堆部分送出保原ID及递增修订的余量；全量送出移除，不留数量0堆。接收方填已有兼容堆，再按逐定义上限创建新堆。跨角色完整转移也新建接收堆ID，不能挪用发送方ID。

新ID为`stack:`加SHA256小写十六进制。摘要输入采用[71确定JSON编码](71-局域网双人交易与恢复采用合同.md)的三元素数组`[settlement_id,character_id,ordinal]`，ordinal为该事件该角色新堆输出的0起连续序号。准备前固定、随原计划持久，重试不重新分配；已有全局堆/实例身份冲突直接拒绝，不覆盖、不回收、不重抽。结算ID由各事件owner唯一分配，不消费玩法随机。

布局先移出全部输入，再计算所有剩余与接收。保自身余量优先；填目标已有堆按稳定槽位/堆ID，新堆放最低空槽。多个来源按输入顺序分配贡献。最终容量、重量、任务最大持有量、受保护数量与预留均须通过；不能只检查单个堆上限。

## 3. 不可变数量流

数量流是唯一正式结算收据内的`stack_flows`数组投影。无堆变动为空数组，单种流一个元素，兼有消费与铸造时按消费、铸造顺序恰两个元素。历史输出保存当时角色和完整堆快照；当前容器只引用仍未被后继消费且按最新已提交域迁移/数量结算属于持有域的输出；复购保管域单独闭合。历史快照不作为第二份库存，不重新实例化。

普通流的`receipt_id`等于原结算ID。每个输入精确引用旧收据ID及输出索引，输入的是**整个旧版本**。部分消费也先消费整个旧版本，再输出新修订余量。输入不得重复，也不能被另一个已提交事件再次消费。

每个输出记录`character_id/stack/contributions/custody`，贡献项为`input_index/quantity`，同输出不能重复输入索引。非铸造流满足：

- 每输出数量＝全部贡献数量之和。
- 每输入原数量＝它在全部输出中的贡献＋明确终结的数量。
- 贡献的定义、绑定、任务作用域与输出一致；角色绑定物的角色也必须一致。
- 每个存续旧ID只有一个输出，来自同ID/同角色前版本且修订恰加1；新ID未曾使用且修订0。
- 每个输出的`origin_receipt_id`等于本流ID；历史依赖只沿inputs前行，不把该自指视为循环。

终结原因包括使用、制作、交付、任务清理、不可复购的NPC出售、确认丢弃、配置移除及复购保管清理。未知原因不能归为普通使用。配置改定义或解绑须显式移除原物并以配置授权授予新物，不能伪装成守恒合堆。

铸造流的输入及终结为空、输出非空且贡献为空；`mint_authorization`精确引用创建礼包、旧档导入、购买、掉落、采集、任务奖励、制作或配置的真实授权收据。必须验证授权的物品、数量、绑定、领取去重与事件类型，写一个来源字符串不构成合法证明。

制作、任务状态替换等既消费又授予不同定义时，同一原子结算内保存两个投影，ID固定为结算ID加`:stack:consume`与`:stack:mint`。仅存在一种流时仍用结算ID。两个投影不是两次经济提交，不允许只发布一半；每个投影对应堆来源引用自身ID。

升天初始化另有[专用退款事件](contracts/升天武功初始化事件.schema.json)：ascension_skill_reset仅授权原已提交初始化真实S颗天机石。固定consume/mint，确需合原石时再有:stack:merge第三流；第三流消费原石与本事件较早mint输出。所有流同一次提交，允许这条有序依赖，拒绝自引/前向/循环和双消费。中间mint堆被合并消费后不作为当前库存；新ID序号跨三流连续，容量按最终布局检查。其他owner不因本例自动获得第三流或退款授权。

示例：原99份送40，接收方原80且上限99。输入两旧版本99/80，输出发送方59、接收方99及新堆21；接收方99由自身80加发送方19贡献，新堆21由发送方21贡献。总量179保持不变，每个输入版本只消费一次。

## 4. 保存、交易与保管边界

当前堆逐字段匹配其来源输出，依赖索引有效、图无环，并验证单次消费。新角色礼包和四组已知旧档导入只按实际物品生成授权输出，空包不生成假发物事件；读新格式不按现物补历史。

[71交易](71-局域网双人交易与恢复采用合同.md)的唯一计划包含双侧流及所需来源闭包，纳入同一摘要、准备守卫和房主决定。接收方合堆时，其原堆来源也必须进入闭包；双方各持自己当前堆所需的完整前链。历史中出现另一角色的输出不等于本角色持有它。commit后只重放原结果，不再拆堆、抽取ID或分配贡献。

普通日志引用唯一数量投影；压缩不能以哈希取代仍需验证的数量和所有权证据。仅凭一侧离线档案无法证明对方未双花，跨角色有效性依赖71协议的唯一决定与守卫，不将闭包称为防篡改签名。

支持复购的堆出售后进入保管域，保留原版本而非先销毁再铸造；FIFO淘汰或角色会话结束时才终结剩余数量，关闭商店面板保留。保管及崩溃恢复设计见[NPC复购JSON](contracts/NPC复购.v1.json)；完整域迁移与经济收据结构仍待，不能把本schema当完整复购结构。

## 5. 验证门槛与剩余范围

结构验证必须覆盖缺字段、未知字段、0/负数/超界、空白身份、错误任务维度结构、不绑定任务物、非法输入输出和铸造/非铸造分支。严格JSON整数token、定义绑定集合、来源授权、图无环、输入单次消费、数量与所有权守恒须另外验证，JSON Schema的integer不能单独拒绝1.0。

计划验证部分/全量拆合、不同任务轮次不合并、99/80送40算例、跨角色新ID、整堆移仓不造来源、两投影原子提交、满包净布局、重复命令/旧版本消费、缺失闭包与LAN故障。这些门槛须在Godot实现后执行，文档算例不替代运行结果。

完整档案、容器、全部唯一实例、经济收据根结构、复购保管与终结、逐producer授权、剩余目录及实际保存/LAN仍待。此合同不宣称D1、物品系统或项目完成。


## 6. 持有与复购保管的迁移证据

[物品域迁移JSON](contracts/物品域迁移.v1.json)及[单条迁移schema](contracts/物品域迁移.schema.json)明确两种逻辑域：held只有kind，buyback另有session_id和sale_receipt_id。每个历史堆流输出必须声明产出域；正常铸造只允许held。域不包含背包槽号，不在当前堆七字段里复制位置。

原样整堆或实例移入保管、原样全量复购，以同一正式事件的custody_transfers记录character_id/kind/target_id/body_revision/previous_custody_receipt_id/from/to。前后域必须不同、一个held一个buyback，正文所有字段均保持相同；角色/库存修订按原事件增加，正文修订不变。前域必须来自最后已提交赋域或迁移，不能引用原创建事件跳过后续出售。

部分出售/复购/合堆有数量变化时，只由flow输出custody赋域，不对同ID再写一条原样迁移。原ID余量在原域，实际转出分量到目标域。清理只能消耗当前buyback输入；使用/制作/交付/普通出售只能消耗held，不能拿历史来源输出当当前可用实物。

每个物品当前恰处于一个域；持有域闭合正式正文/位置，保管域闭合角色会话/原售出记录。迁移前状态单次消费、正文修订、事件顺序、域和队列、钱物/水位全部联合校验并同笔发布。恢复须保完整正文及迁移/数量前链，不能靠哈希或持有快照猜测。完整经济根、实例修改/终结和实际落盘/LAN故障仍待，迁移schema不替代它们。

唯一实例另由[73来源与终结](73-唯一实例来源与终结校验合同.md)采用完整前后正文及版本/终结投影；不借用堆数量守恒表示单件分裂。原样域迁移仍沿本合同，完整经济事件/producer授权/时钟与实际落盘仍待。

通用结算ID预留见[身份合同](contracts/结算身份.v1.json)，贸易及会话等具名算法保持原值。数量流的receipt_id及新堆ID沿实际唯一结算，不为消费/铸造投影再次预留业务计数；完整日志/请求去重索引和持久恢复仍待。
