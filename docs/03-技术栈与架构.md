# 技术栈与架构

更新日期：2026-11-13。目标技术栈固定为 **Godot 4.7.2 标准版 + 类型化 GDScript**。当前 `src/` 仍是 Rust / Bevy 实现，本文描述待落地架构，不表示已经迁移。

## 1. 技术选型

| 层次 | 目标实现 |
| --- | --- |
| 引擎与语言 | Godot 4.7.2 标准版、GDScript；不引入C#、.NET或Rust运行时 |
| 组织方式 | 场景树、节点、信号、Resource与独立RefCounted规则对象 |
| 渲染 | Forward+ / Vulkan，Windows x64；明确配置，不静默改渲染器 |
| 逻辑时间 | 60Hz `_physics_process`，渲染帧不决定规则结果 |
| 碰撞与导航 | 保留圆形脚印对AABB连续扫掠/滑动、镜头线段遮挡、2m格A*，移植为GDScript |
| 配置 | JSON、显式结构/类型/数值/引用校验，替代RON/Serde |
| 界面 | CanvasLayer、Control、Container、Theme、InputMap与焦点路由 |
| 局域网 | ENetMultiplayerPeer/高层多人API、UDP、房主权威逻辑、可靠事务/频道与位置同步分离 |
| 模型与动画 | glTF2.0/GLB、AnimationPlayer/AnimationTree、Skeleton3D、BoneAttachment3D |
| 音频 | AudioStreamPlayer/AudioStreamPlayer3D、AudioServer音频总线 |
| 持久化 | JSON、FileAccess、DirAccess；本地档案及角色快照 |
| 校验 | Godot无窗口规则/场景测试、资源合同、原生渲染、故障注入与导出包检查 |
| 资源工具 | 现有Blender/Python生产脚本按需复用，不作为游戏运行依赖 |

[官方4.7.2发布页](https://github.com/godotengine/godot-builds/releases/tag/4.7.2-stable)已核对。编辑器、控制台程序和导出模板必须同版本；启动检查 Engine 版本，不把 `project.godot` 的4.7系列特性标签当作补丁版本锁定。

## 2. 平台与工程入口

首个目标为Windows10/11 x64，默认1600×900、最小1280×720、垂直同步开启。Linux、macOS、移动端和手柄尚不属于已支持平台。运行包离线工作，无HTTP服务、数据库、浏览器或外部脚本解释器。

以下为规划结构，按阶段创建实际需要的文件，不预建空模块：

| 路径 | 职责 |
| --- | --- |
| `project.godot`、`scenes/main.tscn` | 引擎配置、InputMap、主入口 |
| `scripts/app.gd` | 加载、档案、选角、游戏、错误及会话生命周期 |
| `scripts/data.gd` | 配置合同、资源清单、引用和启动检查 |
| `scripts/profile.gd`、`scripts/save.gd` | 本地档案、角色创建/选择、快照、迁移和提交 |
| `scripts/gameplay/` | 角色成长、职业、武功气功、物品装备、铁匠、任务、门派、战斗、AI与掉落 |
| `scripts/world.gd`、`scripts/presentation.gd` | 地图与实体表现、模型、武器/披风、动画及反馈 |

## 3. 规则与表现边界

GameSession持有唯一业务状态。角色、敌人、背包、装备、任务和随机序列由规则对象管理；Node3D变换、动画、HUD、地图与音频只同步结果。界面发送命令，不能直接扣款、发奖或改等级。

联机时房主GameSession持有世界及按角色ID隔离的参与者状态，客户端持有权威状态镜像和本地输入/表现；不能让每个客户端各自判怪物死亡。一个连接只控制一个角色，同机多开为多个独立进程/Peer。业务序列、快照、队伍/聊天可见范围及重连按[19合同](19-局域网组队聊天与多开.md)实现；旧“全部规则本进程自行决定”仅适用于离线。

固定步顺序为输入请求 → 规则/AI/时序 → 碰撞移动 → 结算事件 → 表现同步与保存请求。每个请求、命中、死亡、掉落和事务均有唯一标记，防止同帧或重入执行。动画回调不参与伤害、无敌或奖励计算。

规则尽量不依赖场景、渲染、真实时钟或文件系统。配置先校验再生成规则；运行时发现不变量破坏明确失败，不能补默认值、丢弃记录或隐式传送。

## 4. 应用状态与生命周期

状态顺序为Loading → LocalLogin → CharacterSelect/CharacterCreate → InGame，资源或档案错误进入LoadError。InGame只有Playing/Paused互斥状态，模态面板使用单一Panel状态。不同角色永远不共享GameSession。

离线暂停或房主全房暂停冻结规则、AI、冷却、刷新、路径及世界音源；联网个人面板只隔离本客户端输入，房主世界继续。UI保留必要处理。死亡姿态可完成一次，但不继续推进战斗。关闭面板、切换角色和返回菜单清空缓存输入。

时钟明确分为世界模拟时钟与交互时钟：前者只在Playing按60Hz整数步推进，后者在当前角色会话的Playing/Paused均按单调时间推进，仅用于装备组切换等交互防连点。交互时钟不能推进技能、药品、状态、首领或活动时限。界面显示的保存日期不参与这两个时钟；离线均不推进。

角色技能/药品剩余冷却、角色持续效果及讨伐成功增益按剩余世界步保存，装备组切换保存剩余交互时长；重进角色不重置或补满。活动继续恢复逻辑快照，不能借重新创建表现节点刷新规则。具体字段及活动快照边界见[数据与存档](05-数据与存档.md)。

世界节点统一挂在会话根节点；退出等待 `queue_free` 完成，再核对节点、动画、投射物、音源和消息清零。连续10次往返不能累积节点或活动资源。只保留必要的菜单预览，不保留上个角色的表现对象。

## 5. 配置与事务

RON配置一次性转换为JSON，并逐字段核对。正式使用一套配置；不能让Rust旧表与Godot新表长期分别决定规则。全部职业、武器、披风、物品、概率、配方和高阶怪物使用稳定ID与显式前置引用。

交易、换装、强化、合成、转移、制造、学习、任务与门派统一采用“复制相关状态 → 完整检查 → 生成变更 → 一次提交 → 事件/保存”。失败不提交部分资源，随机结算与事务ID一起持久化，重试不会重新获得奖励。

多段伤害、持续效果和投射物使用固定步时间与唯一目标集合。对象有效期、生成上限和退出清理必须有界；性能优化不能移除场外敌人的必要规则或导致穿墙。

## 6. 资源与美术接入

GLB、字体、WAV与许可沿用现有资产来源，导入结果需要Godot独立验证。骨骼、坐标、缩放、命名动画、武器朝向、披风体型兼容、根运动和材质不能继承Bevy结论。

`.godot/`是导入缓存，不提交；必要`.uid`及导入设置随资源维护。发行包排除`.blend`、探针、测试、隔离存档、旧Rust产物和本机工具。正式资源缺失时显示路径与原因，不替换占位模型进入游戏。

## 7. 迁移与验证

先完成文档合同，再实现程序；功能测试通过后进入美术、现代界面与最终渲染验证。程序阶段可使用明确标注的开发几何体验证规则，不将其视作美术交付，也不能在正式加载失败时兜底。

旧源码在对应Godot功能验证前作为参考保留；替换并通过系统测试后清理Rust/Cargo及失效工具。历史验证事实汇总至新记录，不保留重复的旧开发计划和总结。

无窗口通过不能证明Vulkan渲染、中文输入法、听验或参考硬件性能。桌面物理操作继续停止，跳过项记录未执行；用于验证的引擎和辅助进程都需关闭。
