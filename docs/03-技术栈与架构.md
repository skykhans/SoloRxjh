# 技术栈与架构

更新日期：2026-11-16。目标技术栈固定为 **Godot 4.7.2 标准版 + 类型化 GDScript**。Rust/Bevy旧运行时、Cargo清单、旧RON和旧打包/烟测路径已清理；Godot工程入口、正式资源校验和随机序列基础模块已落地，其他模块仍待实现。

## 1. 技术选型

| 层次 | 目标实现 |
| --- | --- |
| 引擎与语言 | Godot 4.7.2 标准版、GDScript；不引入C#、.NET或Rust运行时 |
| 组织方式 | 场景树、节点、信号、Resource与独立RefCounted规则对象 |
| 渲染 | Forward+ / Vulkan，Windows x64；明确配置，不静默改渲染器 |
| 逻辑时间 | 60Hz `_physics_process`，渲染帧不决定规则结果 |
| 碰撞与导航 | 保留圆形脚印对AABB连续扫掠/滑动、镜头线段遮挡、2m格A*，移植为GDScript |
| 配置 | JSON、显式结构/类型/数值/引用校验，替代RON/Serde |
| 界面 | CanvasLayer、Control、Container、Theme、InputMap与焦点路由 |
| 局域网 | ENetMultiplayerPeer/高层多人API、UDP、房主权威逻辑、可靠事务/频道与位置同步分离 |
| 模型与动画 | glTF2.0/GLB、AnimationPlayer/AnimationTree、Skeleton3D、BoneAttachment3D |
| 音频 | AudioStreamPlayer/AudioStreamPlayer3D、AudioServer音频总线 |
| 持久化 | JSON、FileAccess、DirAccess；本地档案及角色快照 |
| 校验 | Godot无窗口规则/场景测试、资源合同、原生渲染、故障注入与导出包检查 |
| 资源工具 | 现有Blender/Python生产脚本按需复用，不作为游戏运行依赖 |

[官方4.7.2发布页](https://github.com/godotengine/godot-builds/releases/tag/4.7.2-stable)已核对。编辑器、控制台程序和导出模板必须同版本；启动检查 Engine 版本，不把 `project.godot` 的4.7系列特性标签当作补丁版本锁定。

## 2. 平台与工程入口

首个目标为Windows10/11 x64，默认1600×900、最小1280×720、垂直同步开启。Linux、macOS、移动端和手柄尚不属于已支持平台。运行包离线工作，无HTTP服务、数据库、浏览器或外部脚本解释器。

以下为规划结构，按阶段创建实际需要的文件，不预建空模块：

| 路径 | 职责 |
| --- | --- |
| `project.godot`、`scenes/main.tscn` | 引擎配置、InputMap、主入口 |
| `scripts/app.gd` | 加载、档案、选角、游戏、错误及会话生命周期 |
| `scripts/config_loader.gd` | 正式资源清单结构、路径、ID和导入类型检查 |
| `scripts/profile.gd`、`scripts/save.gd` | 本地档案、角色创建/选择、快照、迁移和提交 |
| `scripts/gameplay/` | 角色成长、职业、武功气功、物品装备、铁匠、任务、门派、战斗、AI与掉落 |
| `scripts/world.gd`、`scripts/presentation.gd` | 地图与实体表现、模型、武器/披风、动画及反馈 |
| `scripts/ui/` | 登录/选角/创建、HUD、面板、地图、消息、设置和确认事务 |

| `tools/` | 版本、资源、许可与发行工具 |

## 3. 规则与表现边界

GameSession持有唯一业务状态。角色、敌人、背包、装备、任务和随机序列由规则对象管理；随机算法/角色及世界流分区沿[唯一随机合同](contracts/随机序列.v1.json)，不得调用引擎全局随机替代正式序列。Node3D变换、动画、HUD、地图与音频只同步结果。界面发送命令，不能直接扣款、发奖或改等级。

`scripts/gameplay/random_stream.gd`实现合同中的SHA-256计数块、53位拒绝采样、确定概率边界和不可变候选状态。具体战斗、掉落及事务事件尚未接入；模块不替调用方决定随机资格或提交状态。

联机时房主GameSession持有世界及按角色ID隔离的参与者状态，客户端持有权威状态镜像和本地输入/表现；不能让每个客户端各自判怪物死亡。一个连接只控制一个角色，同机多开为多个独立进程/Peer。业务序列、快照、队伍/聊天可见范围及重连按[19合同](19-局域网组队聊天与多开.md)实现；旧“全部规则本进程自行决定”仅适用于离线。

固定步顺序为输入请求 → 规则/AI/时序 → 碰撞移动 → 结算事件 → 表现同步与保存请求。玩家手动徒步按[移动合同](contracts/玩家徒步移动.v1.json)冻结唯一真实输入，原动作占用先验、连续碰撞后保存真实轨迹，全部实体移动完成后才冻结进攻推进队列；自动寻路沿[专用路径owner](contracts/自动寻路与移动.v1.json)；闪避及三种辅助位移已有[专用动作结构](contracts/玩家辅助位移.schema.json)，接纳e0、唯一移动职责与首次阻挡来源沿各原owner；原scope[六表注册](contracts/已采用直接战斗注册表.schema.json)只持唯一正文，五类玩家动作跨四类动作表的占用从根推导；原七字段接纳队列统一处理攻击/闪避/位移/木柴采集与三类AI，竹采集沿原普通攻击命令在实际队首路由，不另建动作队列。[采集owner](contracts/采集动作.v1.json)采用旧根战后冻结队列、逐步推进与木柴资格取消；治疗等其余占用及完整输入/阶段父来源仍待闭合。直接攻击接纳按23原direct_attack_admission_phase：入口冻结候选并按实体ID/玩家命令ID原UTF8排序，先依各owner完成周期到点捕获与过期处理，出血合法末跳须在删除到期源前捕获，不能统一先删再扫当前effects；本步新根保持e0，只推进此前已接纳根。首领新放弃/返回/领取仍在本步战斗结果后重验。原world当前scope伤害批次按23.step_resolution.persisted_batch保存实际未完成项，伤害决定/合法停止与项移除同笔，不另存排序ID/完成索引；普通批后唯一尸毒波依原父阶段恢复。场景父阶段采用23.scope_step_lifecycle及[八字段状态投影](contracts/场景固定步状态.schema.json)：规则计时→直接攻击接纳→移动及到期捕获→战斗→战后活动→收尾；combat内部只用原批phase。进入战斗与建批、离开战斗与清批各同笔，非null阶段须先续完原T才接纳后续权威步。步号沿原world.training_gate_clock_steps唯一世界模拟时钟，场景world_step只观察实际获准T；冻结后T可跳号，每次仍只推进一个实际场景步，不按差值补扣实体效果。父世界调度沿23.world_step_lifecycle及[世界计时与待完成场景联合投影](contracts/世界固定步状态.schema.json)，本T冻结原step_pending_scopes并逐首场景完成，收尾与移除首项同笔；不重复保存完成集合或另一个世界计数。普通公共交通沿[迁移合同](contracts/场景迁移.v1.json)在源场景战后提交，目的地本T不再接纳迁入角色模拟/输入，下一真实世界步才恢复；完整事务来源、强制活动/复活/便携迁移时点与完整world根仍待。每个请求、命中、死亡、掉落和事务均有唯一标记，防止同帧或重入执行。动画回调不参与伤害、无敌或奖励计算。

规则尽量不依赖场景、渲染、真实时钟或文件系统。配置先校验再生成规则；运行时发现不变量破坏明确失败，不能补默认值、丢弃记录或隐式传送。

## 4. 应用状态与生命周期

状态顺序为Loading → LocalLogin → CharacterSelect/CharacterCreate → InGame，资源或档案错误进入LoadError。InGame只有Playing/Paused互斥状态，模态面板使用单一Panel状态。不同角色永远不共享GameSession。

离线暂停或房主全房暂停冻结规则、AI、冷却、刷新、路径及世界音源；联网个人面板只隔离本客户端输入，房主世界继续。UI保留必要处理。死亡姿态可完成一次，但不继续推进战斗。关闭面板、切换角色和返回菜单清空缓存输入。

时钟明确分为世界模拟时钟与交互时钟：前者只在Playing按60Hz整数步推进，后者在当前角色会话的Playing/Paused均按单调时间推进，仅用于装备组切换等交互防连点。交互时钟不能推进技能、药品、状态、首领或活动时限。界面显示的保存日期不参与这两个时钟；离线均不推进。

角色技能/药品剩余冷却、角色持续效果及讨伐成功增益按剩余世界步保存，装备组切换保存剩余交互时长；重进角色不重置或补满。活动继续恢复逻辑快照，不能借重新创建表现节点刷新规则。具体字段及活动快照边界见[数据与存档](05-数据与存档.md)。

世界节点统一挂在会话根节点；退出等待 `queue_free` 完成，再核对节点、动画、投射物、音源和消息清零。连续10次往返不能累积节点或活动资源。只保留必要的菜单预览，不保留上个角色的表现对象。

## 5. 配置与事务

正式运行时只读取JSON。原RON资源登记已替换为`assets/config/resources.json`；旧玩法RON已删除，相关玩法数值必须按采用合同迁移，不能自动沿用或作为另一套运行规则。全部职业、武器、披风、物品、概率、配方和高阶怪物使用稳定ID与显式前置引用。

交易、换装、强化、合成、转移、制造、学习、任务与门派统一采用“复制相关状态 → 完整检查 → 生成变更 → 一次提交 → 事件/保存”。失败不提交部分资源，随机结算与事务ID一起持久化，重试不会重新获得奖励。

多段伤害、持续效果和投射物使用固定步时间与唯一目标集合。对象有效期、生成上限和退出清理必须有界；性能优化不能移除场外敌人的必要规则或导致穿墙。

## 6. 资源与美术接入

GLB、字体、WAV与许可沿用现有资产来源，导入结果需要Godot独立验证。骨骼、坐标、缩放、命名动画、武器朝向、披风体型兼容、根运动和材质不能继承Bevy结论。

`.godot/`是导入缓存，不提交；必要`.uid`及导入设置随资源维护。发行包排除`.blend`、探针、测试、隔离存档、旧Rust产物和本机工具。正式资源缺失时显示路径与原因，不替换占位模型进入游戏。

## 7. 迁移与验证

先完成文档合同，再实现程序；功能测试通过后进入美术、现代界面与最终渲染验证。程序阶段可使用明确标注的开发几何体验证规则，不将其视作美术交付，也不能在正式加载失败时兜底。

旧Rust/Bevy源码、Cargo清单、旧RON、旧打包/烟测入口、依赖许可证副本及编译输出已按用户要求清理。旧行为由合同和参考资料重新实现，不读取或运行旧程序；历史验证事实只用于历史说明，不能计入Godot通过项。

无窗口通过不能证明Vulkan渲染、中文输入法、听验或参考硬件性能。桌面物理操作继续停止，跳过项记录未执行；用于验证的引擎和辅助进程都需关闭。

规则身份由[规则清单owner](contracts/规则清单.v1.json)统一定义：清单覆盖正式JSON和实际运行脚本/导出重映射、场景及规则Resource依赖，先独立枚举核完整集合、逐文件字节校验及语义解析，再计算71确定编码SHA256。握手与原导入恢复共用该身份；当前只有合同及规范向量，P1须落实实际Godot导出路径与加载依赖验证。

采集动作采用docs/contracts/采集动作.v1.json：竹e13落效/e36结束、木柴e180落效；post_combat先固定敌伤取消，再推进旧采集，随后处理新活动/服务输入。原scope注册表扩为六字段accepted_gathers，五类玩家动作跨四动作表联合查询占用；不另建动作包装/占用bool。完整采集接纳/取消父与输入路由仍待。

采集接纳复用原七键统一队列：六请求kind，竹保八键普攻意图在队首处理before路由，木柴用四键明确交互；不冻结前分流或新增队列。原直接攻击结果候选排除明确六竹普攻，采集统一十二键结果引用六表唯一根。死亡/正式end直接写原父ID停止采集并释放本人木柴预留，完整共同父仍待。

战后旧采集推进已落入原scope第八字段post_combat_pending_gather_action_ids_or_null：combat退出同笔冻结旧根UTF8有序全集，post_combat逐队首消费推进/停止证明，空后才进入新拾取/服务输入；非该阶段严格null，无第二时钟/游标/完成集。完整入口/逐项共同父和Godot仍待。
