# 运行与发布

更新日期：2026-11-16。Godot4.7.2/GDScript工程入口已建立，当前工作区仍有Rust源码和旧Windows预览包；正式JSON尚未迁移，所以游戏入口会明确失败退出。旧包不能当作新版本交付。

## 1. Godot开发与校验入口

使用Godot4.7.2标准版，编辑器和导出模板精确匹配。在工程根目录执行：

```powershell
godot --version
godot --headless --editor --path . --import
.\tests\p1_smoke.ps1 -Godot "C:\path\to\Godot_v4.7.2-stable_win64_console.exe"
godot --path . -- --save-dir target/verification/manual-saves
```

`godot`指向实际安装的4.7.2控制台程序；不存在时先配置具体路径，不自动切换其他版本。P1探针验证引擎、主场景、60Hz、输入映射及配置错误路径。当前正式配置未迁移，普通启动会报告缺少JSON并以非零码退出；配置迁移后再验成功启动。

应用默认读取`res://assets/config/`和正式导入资源。用户参数位于Godot的`--`之后；`--save-dir PATH`隔离整个档案目录。缺失配置、资源、引擎版本或存档错误要明确显示原因并非零退出。

## 2. 最终用户启动与操作

目标发行目录包含`SoloRxjh.exe`、Godot资源包、许可、资源清单与本说明；采用嵌入PCK还是外置PCK由导出预设明确，不允许缺包仍显示成功。玩家不需要Godot编辑器、Rust、Blender、数据库或独立后端；单人无需网络，局域网模式需要可达LAN和房主进程。

启动进入本地档案，再创建/选择角色进入江湖。角色创建、升级、职业/装备、铁匠、交易、门派和消息均由本地规则完成。完整按键和面板用途统一见[玩法与功能](02-玩法与功能.md)，本页不维护第二份可能冲突的操作表。

默认档案在`%LOCALAPPDATA%/SoloRxjh/profiles/`；旧单槽`save.json`仅通过明确导入入口读取。备份需在游戏退出后复制整个档案目录；不能只复制某件装备或部分角色字段。

多开与联机计划支持`--instance-id NAME`、`--host --port 24572`、`--join IP:PORT`及`--save-dir PATH`（均在Godot的`--`之后，尚未实现）。例：房主使用`--host --port 24572 --save-dir target/verification/lan-host`，客户端使用`--join 127.0.0.1:24572 --save-dir target/verification/lan-client`。不同实例独立档案根，同一档案禁止双写；端口占用明确失败，不自动换端口。跨机需UDP24572可达，不自动修改防火墙。模式和验收见[19合同](19-局域网组队聊天与多开.md)。

## 3. 导出与包结构

目标预设为`Windows Desktop`，使用4.7.2标准版Windows x64导出模板。预设建立并通过系统测试后执行：

```powershell
godot --headless --path . --export-release "Windows Desktop" target/dist/SoloRxjh-godot-1-windows-x64/SoloRxjh.exe
```

发布工具负责创建全新输出目录、拒绝覆盖既有版本、生成SHA256资源清单并打包ZIP。导出包含实际引用的场景、脚本、JSON、模型、材质、字体、音频及许可；排除测试入口、开发几何、探针、`.blend`、用户存档、缓存、旧Rust输出和本机工具。

Godot引擎许可和随附第三方声明需随发行包保留，字体携带OFL，原创资产来源明确。不能把旧Cargo依赖许可证列表直接当作Godot运行依赖清单。

## 4. 包验收与清理

逐项核对目录/ZIP文件、大小和SHA256，从工程外的独立工作目录离线启动，不以开发机资源路径掩盖缺失。验证本地登录→创建→战斗/升级→装备/披风→任务→保存→退出→重开恢复，含一项铁匠失败与一项满包拒绝。

缺失/损坏资源及存档样本使用隔离目录，错误需有路径与原因；正常退出和验证工具主动终止分别记录。结束检查所有本次启动的引擎、游戏、渲染与辅助进程，不能残留导致用户无法启动。

当前已生成的`target/dist/SoloRxjh-windows-x64.zip`属于旧Rust/P6预览。现有`tools/package_windows.py`和`tools/smoke_windows.ps1`也是旧工具，在P/R阶段替换前不能用于声明Godot版已打包。旧包不包含当前新方案的完整系统。

## 5. 历史源码运行边界

如需只读分析或复现旧版，工具链为Rust1.99.0/Bevy0.17.3，原入口为`cargo run --locked --offline --release`。它启动的是旧实现，不是Godot；本轮文档整理不启动该游戏，不把旧Cargo结果计入目标版测试。

最终交付状态、真实命令与未验项见[实施与验证记录](09-实施与验证记录.md)。

正式运行包须携带[规则清单合同](contracts/规则清单.v1.json)规定的res://rules_manifest.json；清单按实际导出文件字节及重映射依赖生成并经独立枚举/启动验证。不能将D1规范向量或编辑器源代码摘要当发行清单，资源/许可证与最终包SHA仍单独交付。当前清单生成与导出验证未实现。


## 6. 历史规则发行保留与恢复

[规则清单合同](contracts/规则清单.v1.json)的historical_retention规定：保留每个已正式交付的完整原发行ZIP及包外SHA256交付记录。记录列明确ZIP文件名/完整包SHA256、从包内实际字节验证的rules_hash及protocol/content/engine版本；两个摘要用途不同。新发行使用全新版本目录，不覆盖、清理旧发行，不以源码或只有哈希的清单替代可运行包。包外记录不加入其所摘要的ZIP，避免自包含循环。

档案备份需要同时保留其依赖的原发行物及交付记录；完整包不写入profile或逐角色复制。恢复旧预留时先核发行来源、ZIP SHA和文件完整性，再由原发行程序独立枚举资源/核规则哈希，精确匹配pending/source_proof。原程序还须能完整校验档案版本与写锁/守卫，否则拒绝；不能用旧程序打开不认识的新档案继续写入。

当前程序不动态加载历史脚本/PCK，不自动下载或启动历史exe。规则缺失时显示所需hash/版本并保原档案，匹配发行在独立目录明确启动；未定义跨规则迁移前，历史结果不能直接套入另一规则档案或混连新版房间。已交付规则集没有自动垃圾回收策略，不能因本机暂未发现引用就删除外部备份或其他玩家可能仍依赖的包。上述为P/R实现与验收要求，当前未生成Godot发行包或运行历史恢复。
